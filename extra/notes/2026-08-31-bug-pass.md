# metha: a pass over what the overhaul left behind

Written 2026-08-31, after `69e2b80d`. Companion to `2026-08-28-simplification.md`,
which is the shape; this one is the sweep for bugs in it. The gate is still open
and the 200G corpus is still unmigrated, which matters for exactly one item
below.

Seven fixes. What is worth writing down is not the fixes but where they were:
**five of the seven are in the code the simplification did not touch.** The
planner, the index, the classifier and the package split were rewritten with
tests as they went, and the sweep found nothing in them. What it found was in the
calendar arithmetic underneath the planner, in the request loop's own
bookkeeping, and in the two files in `oai` that predate all of it.

---

## 1. A plan could skip a whole month

The one that loses data, and the only one that had been losing it in production.

`cut` walked an interval by calling `next(start)`, and `next` for a month was
`now.New(t.AddDate(0, 1, 0)).BeginningOfMonth()`. Go normalises 31 January plus
one month to 3 March. So a plan whose first window began on a 29th, 30th or 31st
committed that day and then jumped to the month after next.

Concretely, and this is a plain daily-granularity endpoint doing nothing unusual:

    run on the 31st of August   ->  window [Aug 31, Aug 31], partial
    run on 5 September          ->  [Aug 31, Aug 31], then [Oct 1, ...]

September is not fetched. Worse, it is not fetched *later* either: the resume
point moves to the start of the next unsettled window, which is now past the gap,
so nothing ever comes back to it. Verified against the real binary and a local
endpoint - the old build asks for `2023-01-31..2023-01-31` and then
`2023-03-01..2023-03-31`, with February simply absent from the server log.

The fix is not to spell the arithmetic more carefully. `period` had two
functions, "the end of the unit t is in" and "the start of the next one", and a
gap is what it looks like when two definitions of the same boundary disagree.
There is one boundary, so there is one function: `next` is `end` plus a
nanosecond, and the cut is gapless by construction. It also retired a 1ns gap
between every pair of windows that nobody had noticed, and a fall-back DST hour
where `BeginningOfHour(t.Add(time.Hour))` walks *backwards*.

`TestPlanIsGapless` did not catch this because every row started on 1 January.
The resume point is now the axis it varies, and every value on it is a day a
month can end on.

## 2. `MaxRequests` compared for equality

    if h.Config.MaxRequests == i {

`i` starts at zero. The simplification note tells this exact story about
`MaxEmptyResponses` - "a harvest driven from Go rather than from the flags
stopped after one request" - and the line two screens above it had the same
shape and was not looked at. A zero `MaxRequests` broke out of the loop *before*
the first request and then committed the window, so the range was recorded as
harvested and empty and the next run resumed past it. Only the flag default of
1048576 kept this off the command line; `metha.NewHarvest` sets three fields and
this is not one of them.

Zero now means no limit, which is what a caller leaving it alone means by it.

## 3. Nothing skipped a window that was already covered

`Writer.HasWindow` is documented as "reports whether a range has already been
harvested, so that a re-run can skip it". Nothing called it but `Migrate`.

The plan resumes from the earliest window that is not final, which is how a
failure in the middle of a range gets retried at all. Everything after that
failure has usually been fetched already, and the driver refetched all of it on
every run until the bad window succeeded.

That is the cost. The correctness problem is what happens when the segmentation
changed between the two runs - `--daily` added to an endpoint that got slow,
which is the ordinary reason to add it. A refetched window supersedes the row
that matches it *exactly*; a daily window inside a settled monthly row matches
nothing, so it is added beside the row it overlaps, and the records under the
overlap are then named by two extents and read twice. `metha cat` emits them
twice and `metha stat` counts them twice.

One line in the driver, and the index stays a coverage map.

## 4. An error status leaked its connection

`DoContext` returned the `HTTPError` before `defer resp.Body.Close()`. Every
4xx and 5xx leaked the connection it arrived on - and `retryable` asks for 500,
502, 503 and 504 to be repeated, so a struggling endpoint leaked one per retry.
Over a sweep of a quarter of a million URLs that is the descriptor limit.

Two lines swapped. While there: `RequestError` is always nil on that path, so
every such message ended in `: <nil>`.

## 5. `Repository.Sets` could loop forever

    if !resp.HasResumptionToken() { break }
    token = resp.GetResumptionToken()

Those are two different questions. `GetResumptionToken` drops a token whose
cursor has reached `completeListSize` - which is how a well-behaved endpoint
says the list is complete, and `HasResumptionToken` still says yes to it. So the
empty token repeated the very first request, which answered the same way, and
`metha id` against such an endpoint appended the same sets to a slice until it
ran out of memory. The loop turns on the token it is about to send now.

`Formats` had the same shape and could not reach it: `ListMetadataFormats`
carries no resumption token, so the loop was one iteration with a second
request's worth of ceremony around it. It is one request.

## 6. `metha stat` on an unharvested endpoint reported zeroes

`Records` answers `ErrNotHarvested`, on the argument that silence "would read as
an endpoint that has no records, which is the one answer that is both wrong and
plausible". `Stat` did not ask, and printed a full report of zero windows, zero
records, zero failures and nothing on disk - which is precisely that answer, at
greater length. A mistyped URL and the wrong `--format` are far likelier than an
endpoint that answered with nothing.

## 7. Two error messages spelled an identity the way a directory name does

`Identity.String` is the `set#format#baseURL` form the pre-1.0 directory names
base64 - it exists for `legacyDir` and is documented as such - and both
`ErrNotHarvested` sites formatted an identity with `%v`. An unset set left the
message opening with a bare `#`:

    metha: #oai_dc#http://export.arxiv.org/oai2: store: nothing harvested
    metha: http://export.arxiv.org/oai2 (format oai_dc): store: nothing harvested

## what this says about the sweep

The simplification note ends on the claim that the moves bought "fewer places a
decision is made". This pass is evidence for it in a backhanded way: the places
where a decision is now made once - `Plan`, `classify`, the index - had no bugs
in them. Every bug was in something with two definitions of one thing (the two
halves of `period`, the two questions `HasResumptionToken`/`GetResumptionToken`
answer), or in a counter compared with the wrong operator, or in an ordering
between two statements that reads the same either way until it doesn't.

The one thing worth generalising: **items 1 and 2 are the same bug twice, and
item 2 is the same bug the note already tells a story about.** A fix written up
as a war story is not a fix applied to the class. Both were boundary conditions
on a counter or a calendar - `==` where `>=` was meant, "the start of the next
unit" derived independently of "the end of this one" - and both were invisible
to a test suite whose inputs all started at a round number.

None of this changes the on-disk shape, so the gate stays open and the migration
is still the next thing.

## the linter, and what it was hiding

`golangci-lint run` reported six errors, five of which said that a method
promoted from an embedded stdlib type did not exist - `v.Add` on a `Values` that
embeds `url.Values`, `hook.Write` on a `CopyHook` that embeds `io.Writer`. That
is valid Go and compiles; the sixth error is the one that explains the other
five:

    could not import cmp (export data version 4 is greater than
    maximum supported version 2)

The installed binary was v1.64.8, built with go1.26.5, against a module compiled
by go1.27.0. It could not read the current stdlib's export data at all, so `io`,
`net/url` and `cmp` were unloadable, every type embedding one of them was
invalid, and their methods were "undefined". Nothing to fix in the code; the fix
is `go install github.com/golangci/golangci-lint/v2/cmd/golangci-lint@latest`,
which builds it with the local toolchain and keeps the two in step. There is now
a `.golangci.yml` saying so at the top, because the failure mode is not
self-describing - it looks like five bugs.

**What it was hiding is the point.** A typecheck failure suppresses every other
linter, so those six lines were standing in front of fifty-seven real findings.
One of them was a bug of the same family as the seven above:

`metha cat` buffered stdout and flushed in a `defer`, which discards what the
flush says. Every byte this command writes goes through that buffer, so the tail
of a corpus reaches the pipe in that one call - and a full disk or a reader that
went away left `metha cat` exiting 0 on truncated output. A pipeline cannot see
that. `metha stat` had it twice, in `report` and in the cache-wide table.

The rest was policy rather than defects: `defer f.Close()` on a file opened for
reading, a lock released on the way out of an error path, the `os.Remove` in
`discardIfEmpty` that is already documented as ignorable. Those are now `_ =`
with the reason, which is the useful state - not because the linter asked, but
because a bare discarded error and a deliberate one should not look identical,
and now the next one that appears stands out.

Two settings earned their comments. `max-same-issues` defaults to three, so
fixing three `f.Close` findings hands you three more: the count is never the
truth until it is zero. And `extra/` is excluded - one-off tools, not part of the
binary - rather than left to contribute noise forever.

`go build`, `go vet`, `gofmt -s`, `go test -race` and `golangci-lint run` are
all clean.
